GEML 与 Carve：一个为排版，一个为 agent

Carve .crvGEML .geml

两种语言都诞生于 2026 年，都想在 Markdown 之后再走一步，但方向不同：Carve 为排版和展现优化，追求更丰富的表现力；GEML 为 agent 优化，追求更强的元素操纵能力，它更像一个容器：用同一套地址和标准动作，容纳并操纵文档内外的各种文本形式。本页把它们的 82 个语法构造和每一项能力逐一摆在一起，标出各自的设计来源，再用两边的官方解析器跑同一批输入。两者写法相同的地方只有 13 条，全部来自更早的公共来源；其余部分各自成体系。

13写法相同的 13 条，都来自公共来源

ATX 标题、[t](url)、![](src)、`code`、[^id]、- [ ]、{#id .class k=v}、%% 等，分别来自 Markdown（2004）、PHP Markdown Extra、GFM、Pandoc、Obsidian/Mermaid、CommonMark。

29 · 11各自的独有写法互不重叠

Carve 独有 29 条：/斜体/ *粗体* _下划线_ =高亮=、|= 表头、^ 题注、::: 容器、</#id>、CriticMarkup 等。GEML 独有 11 条：类型块原语、数据形态表格、view、data、块内坐标、带标签闭合等。同一段文本两边的解析结果完全不同（实测 P7）。

两个方向一个为排版，一个为 agent

Carve 是 Djot 的继任者，力气花在内联表现、表格版式、题注编号和多种输出上。GEML 的力气花在地址、按块读写、写入护栏、块级历史和引用校验上，让 agent 能精确、安全地改动文档里的任何一个元素。

相反关键设计决定方向相反

Carve 否决了 {{name}} 变量，GEML 把 {{key}} 放进核心；Carve 让找不到目标的引用原样留给宿主，GEML 规定它是构建错误；Carve 默认放行 =html，GEML 没有 HTML 通道。

09-30两个项目何时知道对方

Carve 的仓库里没有任何关于 GEML 的记录。GEML 第一次记下 Carve 是 09-30 的一份同类项目调研，那时 GEML 的核心设计都已上线一到三个月。

229profile 与 view 都是一步步重构出来的

profile 从写进核心规范，到 08-31 抽成应用层机制，六个 profile 累计 229 次提交；view 从 table 的计算属性拆成独立的块。详见第五节。

一 · 设计方向

一个为排版，一个为 agent

Carve 想让文档呈现得更好，GEML 想让 agent 能精确、安全地改动文档里的每一个元素。左右两栏是两边各自投入最多的地方；下表是由此带来的设计取舍，每一行都引自两边各自的文档或首个提交。

Carve为排版与展现优化

投入集中在「一份文档能呈现得多好」。

  • 内联表现力下划线、高亮、上下标、粗斜体、语义 span（kbd、abbr、time）、语言标注、提及与标签。
  • 排版细节智能标点（破折号、省略号、箭头、©）、不换行空格、诗歌行块、续接标记。
  • 表格版式合并单元格、水平与垂直两轴对齐、续行、表头与表尾行数。
  • 题注与编号图、表、代码清单、公式的题注，Figure # 自动编号，复合图面板。
  • 编辑痕迹CriticMarkup 的插入、删除、替换与批注。
  • 多种输出HTML、Markdown、纯文本、ANSI 终端，并报告每种输出丢了什么。

GEML为 agent 操纵元素优化

投入集中在「一个程序能多精确、多安全地改动文档里的一个元素」。

  • 一切皆有地址显式 id、标题推导 id、两块之间散文的派生地址、内容地址 @<hex>、块内坐标 #t[2]["Q1"]、行号选择 L27-58。
  • 按地址读写get / set / add / delete / rename / revert 只动目标块；实测改一格，400 字节里 399 字节原样不动（P9）。
  • 写入有护栏每次写入前整份重查，结果不能解析就拒绝；#id@<hex> 拦住基于过期内容的写入；rename 同步改掉全部引用。
  • 改坏能退.gemlhistory 版本链，单块回滚，整链可重算校验。
  • 引用是契约八类引用在构建期校验，agent 改完一块立刻知道有没有弄断别处（P1、P3–P6）。
  • 数据可推导table、view、data 与绑定的图表：改一个数，汇总和图跟着变。
  • 给 agent 的接口MCP 的 11 个读写工具与 agent 技能；读一块只占一块的上下文（实测 133 B / 400 B）。

GEML 更像一个容器

同一套地址和标准动作，既作用于文档里的各种文本形式，也伸到文档外的文件、数据、代码库和其他文档。

文档内 · 容纳的文本形式
  • === code 任意编程语言，原样保存
  • === math TeX 公式
  • === diagram mermaid、vega-lite 等外部 DSL
  • === table 管道表、CSV、TSV
  • === data JSON、JSONL（YAML、TOML、EDN 已预留）
  • === meta 带类型的键值
  • === note、=== text 流式正文
  • 不认识的类型：告警，正文原样保留
GEML 文档

一种围栏 === type {attrs}，由类型注册表决定正文按 raw、flow 还是键值来读。

命令行、MCP（工具名就是命令路径，07-29 起）和各 profile 的动词共用这一套。

文档外 · 伸出去的引用
  • code src=f.py#L10-20 源码文件的一段，行范围越界即报错
  • table src=data.csv 本地或 http(s) 的数据文件
  • data src=log.jsonl#L1-500 JSON、JSONL、YAML 文件的一段

  • embed src=doc.geml#id、[[doc.geml#id]] 其他文档里的块；get --view 可直接读穿嵌入
  • profile 伸得更远：codemap 把整个代码库写成文档，media 管音视频素材，translator 让另一种语言的文档成为投影

向下兼容 Markdown：内联写法沿用 Markdown；.md 文件不必转换就能 list、find、get、set，写进去的仍是 Markdown 语法（10-02）；需要时一条 geml notes.md 就能转成 GEML。

Carve 的模型是「一份标记文档渲染成多种输出」。引入处理器只收 Carve 或纯文本，由宿主在解析器之外展开，核心解析器不读文件；命令行的动作作用于整篇文档（render、fmt、lint、diff、merge、migrate、flatten），按块的读取与替换 10-05 才出现在它的 MCP 服务器中。

五 · 设计演进

GEML 自己的几次重构

GEML 的结构不是一次定型的。下面三次重构都由它自己的问题推动：第二个实现能否与参考实现对齐，以及一个不认识新语法的处理器会不会显示错误的内容。

Profile：从写进核心，到应用层词汇表

  1. 06-17.gemlhistory 作为「配套规范」与核心规范并列它的三种块类型在哪里都没有声明，7 个旁车文件累计报出 333 条去不掉的「未知块类型」警告。
  2. 07-01 起代码图写进核心渲染器geml-code-graph 和规范自己的 geml-chart、mermaid 挂在同一条 if 链上；codemap、media、style 的命令各占一个 else-if；参考实现里还有一张规范没写的注册表在压掉诊断。
  3. 08-30GEP-0008 先把 form 当作核心块类型提出
  4. 08-31§8.6 profile 机制（GEP-0009）文档用 meta 里的 profile 声明词汇表；词汇表只许可名字，不得改变文档模型；禁止从扩展名推断；history 成为第一个 profile。一致性套件用一个谁都不认识的词汇表名来验证：不实现 profile 机制的第二个实现也能复现全部用例。
  5. 09-04 → 09-16form、translator、media 进入 profileform 改为 geml-form/v1 的 form-* 家族；09-07 translator，09-16 media。
  6. 09-17profile 治理命名、状态、检查、一致性测试。
  7. 09-18核心不再按名字认识任何词汇表渲染、命令、meta 键三处改为查表，支持运行时注册。render.ts 的 2,894 行里有 1,683 行属于代码图，搬出后降到 1,125 行，没有图的页面小了 46%。

Carve 的 profile 从 Init 起就是另一回事：沿用 djot-php 的内容限制预设（full / article / comment / minimal），用于过滤不可信输入。

View：从 table 的属性，到独立的块

  1. 06-17初稿把 compute= 写在 table 上「表格双形态 + 可移植计算」。
  2. 06-18加上 summary 汇总行与 printf 显示格式
  3. 09-03GEP-0012 草案仍把 where / order / limit / select 放在 table 上
  4. 09-04改为独立的 view 块（parser 1.10.0）理由经过逐项衡量：不认识 where= 或 select= 的处理器会显示作者想排除的行和列，这不是降级而是错误的渲染；没有正文的 view 被忽略时什么都不显示。compute=、summary= 和指向块的 src= 全部移到 view，table 只放事实，再带这些属性就报 unknown-attribute。规范自身的诊断从 6 个错误降到 4 个。

Output：从专用块，到通用嵌入

  1. 06-18=== output 保存代码块的运行结果处理器从不执行，只保存，可用 of=#id 绑定代码块。
  2. 07-31撤回 output，改为 === embed {src=doc.geml#id}任意块都能被嵌入，src= 与 data= 并成一条规则。

Carve 的表格没有计算能力，图表数据写在 JSON 里；它的引入处理器 {{ path #id }} 从 Init 起就是现在的写法，09-14 成为规范。

六 · 各自所长

独创与更强之处

只列有实测或规范条文支撑的项。两边的长处并排看，就是两种不同的设计目标。

GEML独创或更强

  1. 一种围栏承载全部结构化内容=== type {attrs} 加类型注册表，正文按 raw / flow / 键值三种模式处理；06-17 初稿第一条设计目标。
  2. 引用是契约，不是建议八类引用全部在构建时校验，断了就是错误。实测 P1、P3、P4、P5、P6 中 Carve 均放行。
  3. 每一块都有地址，并且可写显式 id、标题推导、两块之间散文的推导地址；get / set / add / delete / rename / revert；写入前验证可解析。Carve 同类工具晚三个月，只有读取与替换。
  4. 块级版本历史.gemlhistory 哈希链，可校验、可单块回滚（实测 P9）。Carve 没有任何存储的历史。
  5. 文档里的数据关系层表格的数据形态与外部源、view 推导、计算列和汇总行、data 块、按列校验的图表。Carve 的图表只能内嵌写死的 JSON。
  6. 元数据是带类型、可校验的值=== meta 与 {{key}}：这正是 Carve 明确否决的方向。
  7. 应用层词汇表与投影form、media、style、translator、codemap 在核心之上扩展；中文规范本身就是英文规范的翻译投影。
  8. 向下兼容 Markdowngeml list / find / get / set 直接作用于 Markdown 文件，写入仍是 Markdown 语法；需要时一条命令转成 GEML。

Carve独创或更强

  1. 丰富的内联写法斜体、粗体、下划线、高亮、上下标、CriticMarkup、智能排版、提及与标签、语义 span。
  2. 表格排版合并单元格、两轴对齐、续行、表头与表尾行数。
  3. 题注与自动编号图、表、代码清单、公式的 ^ 题注，Figure # 编号，复合图面板。
  4. 三套逐字节一致的实现JS、PHP、Rust，外加 Go、Python、Ruby 绑定，2,223 对测试样例。
  5. 生态覆盖面十余种编辑器、数十种框架与静态站点集成、PDF 与 LaTeX 输出。
  6. 格式桥与损失报告从 HTML、Markdown、Djot、BBCode 导入；输出时报告丢失了什么。
  7. 不可信输入的内容限制profile 预设、链接策略、安全模式。
  8. 三方合并carve merge 合并两条独立的 AST 修改。

两个项目何时知道对方

  • Carve 全部分支的历史与文件中没有 GEML 的任何记录。
  • GEML 第一次记录 Carve 是 09-30 的同类项目调研，同一份调研还比较了 Djot、VersaDok、Pandoc、MyST、Markdoc、mq 等。此时类型块、引用校验、按块读写、版本历史、数据层、MCP 都已上线一到三个月。
  • 调研列出 Carve 有而 GEML 没有的两点：行内元素带 id、写入前核对预期哈希。行内 id 至今没有加入 GEML。
  • 同日晚些时候，GEML 让 #id 与 08-04 起就有的内容地址 @<hex> 组合成写入守卫（4ddb3eed），提交说明注明参照 mq 的查询语言；这类带预期值的写入与 HTTP If-Match 同理。
