The Markdown Variants Map

mundimark/awesome-markdown collects projects that set out to patch or replace Markdown, and GEML itself is in its "Beyond Markdown" section. This page looks at them one by one: what each does, where it collides with GEML, and where it goes another way. A few projects off the list are closer to GEML; they are included too, marked separately.

Verdict. No project does all three of GEML's things at once: one typed block, an addressable id on every block, and references checked at build time and before every write, with an error stopping the write.

Taken one at a time, each has been done earlier or deeper than in GEML. Generic blocks with attributes are common ground for Djot, Pandoc, MyST and Markdoc; validation with rule ids exists in Markdoc, mystmd and Carve; and querying and rewriting Markdown by selector is more of a language in mq than in geml get. Where GEML differs is binding the three together, and adding a command line that writes by block, MCP, and per-block history.

Closest in features is Carve, but its reach is still small. It sits in the same section of the list as GEML, was created only this May, and already has lint, a JSON AST, patch-based editing, an MCP server and an agent skill — it is moving fast; but it has only 32 stars and no outside users could be found. Weighed by reach, it is a project worth tracking, not the main rival for now. It differs from GEML in three ways: its addresses are heading ids and AST paths, writes go through confirmed patches, and it is not Markdown-compatible.

Blocks

Everyone arrived at "one generic block plus attributes"

Markdown's blocks are special cases, one by one: code, quotes, lists and tables each have rules of their own. Nearly every successor converged on the same fix: one generic container, told apart by attributes. Where they differ is whether the set of types is open or closed, whether ids have rules, and how the body inside a block is parsed.

References

Everyone has ids; few treat a broken reference as an error

Nearly every variant can give a block an id and link to it. Where they part is what the tool says when a link points at an id that does not exist.

Query

Query and rewrite: by selector, or by id

Taking or changing one part instead of writing the whole file is the core of GEML's command line. Two tools on the list do neighbouring things: mq queries and rewrites Markdown with a jq-like syntax, and darnlink anchors links with UUIDs, so they can be fixed after a file moves.

Embedding

Embedding and sync: pull in, or push back

Putting content from elsewhere into a document is the most common extension people ask for. On the list, mdcode, Slidev, markedpp and MultiMarkdown each have a syntax for it, and AsciiDoc, beyond the list, has one too. They part in two places: whether they refer by line number or by name, and whether a miss is an error.

Extensions

Components and extension points: code into the document, or vocabulary into the document

There are two ways to put a chart, a form or something interactive into Markdown. One lets the document contain component code; the other has the document write only declarations, which a renderer interprets against a vocabulary.

Agents

For agents: in 2026 everyone shipped an MCP

"Let an agent read and write one part instead of rewriting the whole" became common ground this year. Slidev added an MCP in July, Carve's MCP was created in September, and mq and demarkus each have one. They differ in three places: whether the address is stable, whether a write is checked first, and whether a bad change can be rolled back.

Revisions

Record a change in the text, or beside it

CriticMarkup is the only project in the list's syntax-extensions section that deals with revisions.

Takeaways

What it means for GEML

Four things: what is really unique, which rival to face squarely, what is worth borrowing, and what is no cause for worry.

Unique Three things bound together

Typed blocks, stable ids the author writes, and a whole-document check before every write: each has been done on its own, but only GEML puts them together. Add a command line and an MCP that write by block, per-block history, and reading existing .md directly: Carve and Djot both need the document converted first, and GEML does not.

Closest Carve: close in features, small in reach

Same section, same story: lint, a JSON AST, patch-based editing, MCP, an agent skill. Created only this May, it already has 64 repositories, 2,200 test cases and three implementations, with dozens of commits a day at the end of September; but it has only 32 stars, and no outside users could be found. Weighed by reach, it is a project to track, not today's main rival. It differs from GEML in a stable address on any block, a check on every write, and compatibility with existing Markdown; whenever GEML is presented, those three should come before the syntax.

Reach Weighed by reach

The two head-on projects are both small: Carve has 32 stars, mq 1,040. The big ones are Slidev (48,891), Pandoc (46,456), MDX (19,809) and Markdoc (8,494). Judge the effect on GEML by the latter: Slidev shows that an MCP reading and writing by unit is already in a mainstream tool, and Markdoc is the best frame of reference for presenting GEML.

Worth borrowing Six things GEML does not have yet

Attributes and ids on inline elements (Djot, Carve); referring to a source snippet by name (mdcode's and Slidev's regions, AsciiDoc's tags); pushing code changes in a document back to the source file (mdcode); repairing cross-document references after a file moves (darnlink); pending suggested changes (CriticMarkup); handing the content hash to the caller for a check before writing (Carve, demarkus).

No cause for worry The foundation, and another layer

CommonMark, GFM and VFMD are where GEML's prose comes from; old extensions like MultiMarkdown and Markdown Extra are collections of special-case syntax, which GEML has folded into one kind of block. MDX is the other road, "the document is a program". MarkWay and mk-notes sit at the layer of protocols and sync, not of document formats.

Proposal
By the project's rules, each of the six "worth borrowing" items should have a name and a phase in a design document. Two are the smallest and closest to what exists: have get --json and the MCP return the content hash, for a check before writing with the content address in a selector; and refer to source by region, added to code {src=}.
