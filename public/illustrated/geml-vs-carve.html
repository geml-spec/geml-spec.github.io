GEML and Carve: one built for typesetting, one for agents

Carve .crvGEML .geml

Both languages were born in 2026 and both set out to go one step past Markdown, in different directions: Carve optimizes for typesetting and presentation, for richer expression; GEML optimizes for agents, for stronger control over every element, and works more like a container: one set of addresses and standard actions holds and manipulates text forms inside the document and out. This page lines up their 82 syntactic constructs and every capability, marks where each design comes from, and runs the same inputs through both official parsers. The two share a spelling in only 13 places, all inherited from older public sources. Everything else is its own system, with different goals, trade-offs and capabilities.

1313 shared spellings, all from common sources

ATX headings, [t](url), ![](src), `code`, [^id], - [ ], {#id .class k=v}, %% and a few more, from Markdown (2004), PHP Markdown Extra, GFM, Pandoc, Obsidian/Mermaid and CommonMark.

29 · 11Each language's own constructs stay its own

Carve alone has 29: /italic/ *bold* _underline_ =highlight=, |= header cells, ^ captions, ::: containers, </#id>, CriticMarkup and more. GEML alone has 11: the typed-block primitive, data-form tables, view, data, inner-unit coordinates, labeled closes and more. The same line of text parses completely differently in each (probe P7).

Two directionsOne built for typesetting, one for agents

Carve succeeds Djot and spends its effort on inline expression, table layout, captions and numbering, and many output formats. GEML spends its effort on addresses, block-level reads and writes, guarded writes, block history and reference checking, so an agent can change any element of a document precisely and safely.

OppositeKey design decisions point opposite ways

Carve rejected {{name}} variables; GEML puts {{key}} in the core. Carve leaves an unresolvable reference to the host; GEML makes it a build error. Carve passes =html through by default; GEML has no HTML channel at all.

09-30When each project learned of the other

Carve's repository holds no record of GEML. GEML first noted Carve on 2026-09-30, in a survey of similar projects; by then every core part of GEML had been live for one to three months.

229Profiles and views were redesigned step by step

Profiles went from hard-wired in the core spec to an application-layer mechanism on 08-31, with 229 commits across six profiles; view was split out of a table's computing attributes into a block of its own. See section 5.

1 · Design direction

One built for typesetting, one for agents

Carve wants a document to look better; GEML wants an agent to change any element of a document precisely and safely. The two columns show where each puts most of its effort; the table shows the trade-offs that follow, each row taken from the project's own documents or first commit.

CarveBuilt for typesetting and presentation

Its effort goes into how well a document can look.

  • Inline expressivenessUnderline, highlight, super- and subscript, bold italic, semantic spans (kbd, abbr, time), language tags, mentions and tags.
  • Typographic detailSmart punctuation (dashes, ellipses, arrows, ©), no-break spaces, verse line blocks, continuation markers.
  • Table layoutMerged cells, horizontal and vertical alignment, continuation rows, header and footer row counts.
  • Captions and numberingCaptions for figures, tables, listings and equations, Figure # numbering, composite figure panels.
  • Editorial marksCriticMarkup insertions, deletions, substitutions and comments.
  • Many outputsHTML, Markdown, plain text and ANSI terminal output, each with a report of what it dropped.

GEMLBuilt for agents that manipulate elements

Its effort goes into how precisely and safely a program can change one element of a document.

  • Everything has an addressExplicit ids, derived heading ids, derived addresses for prose between blocks, content addresses @<hex>, inner-unit coordinates #t[2]["Q1"], line selectors L27-58.
  • Read and write by addressget / set / add / delete / rename / revert touch only the target block; changing one cell left 399 of 400 bytes untouched (P9).
  • Guarded writesEvery write rechecks the whole document and is refused if the result would not parse; #id@<hex> stops a write based on stale content; rename updates every reference.
  • Undo what brokeA .gemlhistory revision chain, single-block revert, a chain that can be rehashed and verified.
  • References are a contractEight kinds of reference are checked at build time, so an agent that edits one block learns at once whether it broke another (P1, P3–P6).
  • Data that derivestable, view, data and the charts bound to them: change one number and the totals and the chart follow.
  • An interface for agents11 read/write MCP tools and an agent skill; reading one block costs one block of context (measured 133 B of 400 B).

GEML works more like a container

One set of addresses and standard actions reaches the text forms inside a document and the files, data, codebases and other documents outside it.

Inside the document · forms it holds
  • === code any programming language, kept verbatim
  • === math TeX
  • === diagram external DSLs such as mermaid and vega-lite
  • === table pipe grid, CSV, TSV
  • === data JSON, JSONL (YAML, TOML, EDN reserved)
  • === meta typed key-value pairs
  • === note, === text flow prose
  • An unknown type: a warning, with the body kept verbatim
A GEML document

One fence, === type {attrs}; a type registry decides whether a body is read as raw, flow or key-value.

The command line, MCP (each tool name is its command path, since 07-29) and every profile's verbs share this one set.

Outside the document · references that reach out
  • code src=f.py#L10-20 a span of a source file; an out-of-range span is an error
  • table src=data.csv a local or http(s) data file
  • data src=log.jsonl#L1-500 a span of a JSON, JSONL or YAML file
  • data= chart data from CSV, JSON, or a table in another document
  • embed src=doc.geml#id, [[doc.geml#id]] blocks in other documents; get --view reads straight through an embed
  • Profiles reach further: codemap writes a whole codebase as documents, media manages audio and video assets, translator makes a document in another language a projection

Backward compatible with Markdown: inline syntax follows Markdown; .md files can be listed, searched, read and written with no conversion, and what is written stays Markdown (10-02); when needed, geml notes.md converts one to GEML in a single command.

Carve's model is one markup document rendered to many outputs. Its include processor takes only Carve or plain text and is expanded by the host outside the parser, which does no file I/O; its command-line actions work on whole documents (render, fmt, lint, diff, merge, migrate, flatten), and block-level read and replace arrived in its MCP server on 10-05.

5 · Design evolution

GEML's own redesigns

GEML's structure was not fixed in one stroke. Each of the three redesigns below was driven by GEML's own problems: whether a second implementation could agree with the reference one, and whether a processor that does not know a new construct would show the wrong content.

Profiles: from hard-wired into the core to application-layer vocabularies

  1. 06-17.gemlhistory as a "companion specification" beside the coreIts three block types were declared nowhere, so seven sidecars reported 333 "unknown block type" warnings that nothing could remove.
  2. from 07-01The code graph wired into the core renderergeml-code-graph sat on one if-chain beside the specification's own geml-chart and mermaid; codemap, media and style commands each had an else-if; and an unwritten registry in the reference implementation suppressed diagnostics.
  3. 08-30GEP-0008 first proposes form as a core block type
  4. 08-31§8.6, the profile mechanism (GEP-0009)A document declares vocabularies through the profile meta key; a vocabulary licenses names and must not change the document model; inference from a file extension is banned; history becomes the first profile. The conformance suite proves it with a vocabulary name nothing recognizes: a second implementation with no profile mechanism reproduces every case.
  5. 09-04 → 09-16form, translator and media become profilesform becomes the form-* family of geml-form/v1; translator on 09-07, media on 09-16.
  6. 09-17Profile governanceNaming, state, checking, conformance tests.
  7. 09-18The core no longer knows any vocabulary by nameRendering, commands and meta keys became table lookups, with runtime registration. 1,683 of render.ts's 2,894 lines belonged to the code graph; once moved out, the file is 1,125 lines and a page with no diagram is 46% smaller.

Carve's profiles have been something else since Init: djot-php's content-restriction presets (full / article / comment / minimal), for filtering untrusted input.

View: from table attributes to a block of its own

  1. 06-17The first draft puts compute= on a table"Two table forms plus portable computation".
  2. 06-18A summary row and printf display formats are added
  3. 09-03The GEP-0012 draft still puts where / order / limit / select on a table
  4. 09-04A separate view block instead (parser 1.10.0)The reason was weighed attribute by attribute: a processor that does not know where= or select= shows the rows and columns the author excluded, which is a false render rather than a degraded one; an ignored view has no body and shows nothing. compute=, summary= and a src= naming a block all moved to view; a table holds facts only and reports unknown-attribute if it carries them. The spec's own diagnostics went from 6 errors to 4.

Output: from a dedicated block to general embedding

  1. 06-18=== output stores a code block's captured resultNever executed, only stored, optionally bound to its code block with of=#id.
  2. 07-31output withdrawn in favour of === embed {src=doc.geml#id}Any block can be embedded, and src= and data= become one rule.

Carve's tables do not compute, and its chart data lives in JSON; its include processor {{ path #id }} has had its current spelling since Init and became normative on 09-14.

6 · Strengths

What each does that the other does not, or does better

Only items backed by a run above or by spec text. Side by side, the two lists describe two different goals.

GEMLOriginal or stronger

  1. One fence for all structured content=== type {attrs} plus a type registry that reads a body as raw, flow or key-value; the first design goal of the 06-17 draft.
  2. References are a contractEight kinds of reference are checked at build time, and a broken one is an error. In probes P1, P3, P4, P5 and P6, Carve lets the case through.
  3. Every block has an address, and every address is writableExplicit ids, derived heading ids, derived addresses for prose between blocks; get / set / add / delete / rename / revert; each write is checked to parse. Carve's comparable tools arrived three months later and cover read and replace.
  4. Block-level historyA .gemlhistory hash chain that can be verified, with single-block revert (probe P9). Carve stores no document history.
  5. A data layer inside the documentData-form and externally sourced tables, derived views, computed columns and summary rows, data blocks, charts checked by column. Carve's charts embed fixed JSON.
  6. Metadata as typed, checked values=== meta and {{key}}, the direction Carve explicitly dismissed.
  7. Application-layer vocabularies and projectionsform, media, style, translator and codemap extend the core; the Chinese spec is itself a translation projection of the English one.
  8. Backward compatible with Markdowngeml list / find / get / set work on Markdown files directly and write Markdown back; one command converts a file to GEML when needed.

CarveOriginal or stronger

  1. Rich inline writingItalic, bold, underline, highlight, super- and subscript, CriticMarkup, smart typography, mentions and tags, semantic spans.
  2. Table layoutMerged cells, two-axis alignment, continuation rows, header and footer row counts.
  3. Captions and numbering^ captions for figures, tables, listings and equations, Figure # numbering, composite figure panels.
  4. Three byte-identical implementationsJS, PHP and Rust, plus Go, Python and Ruby bindings, against 2,223 test pairs.
  5. Ecosystem reachA dozen editors, dozens of framework and static-site integrations, PDF and LaTeX output.
  6. Format bridges with loss reportsImports HTML, Markdown, Djot and BBCode; reports what an output format dropped.
  7. Content restriction for untrusted inputProfile presets, link policies, a safe mode.
  8. Three-way mergecarve merge combines two independent AST edits.
